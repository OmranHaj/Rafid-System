# RAFID — Implementation Plan

> تحديث مهلة التسليم: بناءً على طلب المستخدم بتاريخ 2026-10-31، يُتبع الآن [نطاق اليومين](MVP_48H.md). البنية والتقديرات أدناه مرجع للتوسع، ولا تصف التطبيق الحالي.

**التاريخ:** 2026-10-31

**الحالة:** خطة تنفيذ مقترحة وجاهزة لتحويلها إلى مهام تطوير؛ ليست تقريرًا عن تطبيق منفذ.

**المصدر:** [وثيقة المشروع v1.0](../RAFID_Project_Concept_MVP_Roadmap.md)، الأقسام 1–20.

**الأولوية:** تنفيذ دورة شراء وتوصيل موثوقة قبل ميزات الذكاء والتحسين المتقدم.

## 1. تحليل الوثيقة

رافد ثلاثة مجالات مترابطة: تجارة متعددة الموردين، إدارة طلبات، وتشغيل توصيل. بناء كتالوج وواجهات فقط لن يحقق تعريف النجاح في القسم 17.

القرارات الصحيحة في التصور والتي يجب الحفاظ عليها:

- فصل تعريف المنتج الموحد عن عرض المورد وسعره ومخزونه.
- فصل الطلب الرئيسي عن طلب المورد الفرعي، وفصل كليهما عن رحلة السائق.
- عزل بيانات الموردين والعروض الخاصة ومهام السائقين على مستوى الخادم.
- مقارنة مواصفات وكميات متكافئة وتكاليف تشمل التوصيل، مع مرجع توفير معلن.
- دعم توصيل المورد وتوصيل رافد، ورحلات متعددة الطلبات ضمن قيود السعة والوقت.
- تأجيل GPS الحي والتمويل والمحفظة وERP والذكاء الاصطناعي وتحسين المسارات الكامل.

الفجوات التي تحول التصور إلى قرارات تنفيذية:

| الفجوة | المعالجة المقترحة | التوقيت |
|---|---|---|
| غياب اختيار تقني وتصميم نشر | بنية موحدة بوحدات مستقلة كما في القسم 3 | M0 |
| عدم تحديد تأكيد السعر وحجز المخزون | عرض سعر مؤقت ثم لقطة طلب وحجز ذري؛ لا زيادة دون موافقة المحل | M0 ثم M3 |
| رفض مورد ضمن طلب متعدد الموردين | رفض الطلب الفرعي فقط وإظهار نتيجة جزئية للطلب الرئيسي | M3 |
| فصل حالات التجارة والتوصيل والشكاوى | آلات حالات مستقلة بدل سلسلة خطية واحدة | M0 ثم M3–M5 |
| تداخل سعات الرحلات مع المحطات | حساب الحمولة على كل جزء من المسار وقفل التعديل المتزامن | M4 |
| عدم تحديد تعريف المنتج القابل للمقارنة | هوية تشمل العلامة والحجم والوحدة والعبوة وعدد القطع | M1 |
| سياسات غير محسومة: العملة والعمولات والإلغاء | إعدادات موثقة واختبارات، مع بوابات قبل التشغيل الحقيقي | M0/M6 |

## 2. النطاق وحدود التسليم

**الشريحة الأولى M0–M4:** دخول وصلاحيات، اعتماد المورد، كتالوج موحد، أسعار ومخزون، منطقة وجدول توصيل، سلة متعددة الموردين، تأكيد وتجهيز، مسارا التوصيل، رحلة متعددة الطلبات، إثبات تسليم، وتتبع وسجل أحداث.

**اكتمال MVP يتطلب M5 وM6 أيضًا:** عروض عامة وخاصة، مجموعات محلات محددة، توصيات وتوفير، بلاغات نقص وتلف، تقييمات، تحصيل نقدي، تقارير أساسية، إشعارات داخلية، واختبار التشغيل الفعلي. لا تُحذف هذه الوظائف باعتبارها تحسينات مستقبلية لأنها مذكورة ضمن نطاق MVP في القسم 8.

**مؤجل:** RFQ والتفاوض، إعادة الطلب، الشراء الجماعي، ذمم متقدمة، حملات آلية، تطبيقات Native، GPS مستمر، تحسين المسار الآلي، مستودعات وتبريد، محافظ وتمويل، تكامل ERP ومؤشر السوق والذكاء الاصطناعي. الشكاوى البسيطة داخل MVP، أما دورة إرجاع وتسوية مالية متقدمة فلاحقًا.

## 3. البنية التقنية المقترحة

هذه اختيارات تنفيذية مقترحة وليست متطلبات واردة في الوثيقة أو قرارات اعتمدها مالك المشروع.

| الطبقة | المقترح | السبب |
|---|---|---|
| الواجهات | Next.js + TypeScript، تصميم عربي RTL، واجهة جوال قابلة للتثبيت PWA | مشاركة المكونات وتغطية الأدوار دون أربعة تطبيقات مستقلة |
| الخادم | NestJS + REST/OpenAPI | وحدات واضحة وصلاحيات ومعاملات مركزية يمكن لتطبيقات لاحقة استخدامها |
| البيانات | PostgreSQL + Prisma ومهاجرات محفوظة في Git | علاقات وقيود ومعاملات للطلبات والمخزون |
| العمل المؤجل | جدول Outbox وعامل معالجة في البداية | إرسال الإشعار بعد نجاح المعاملة مع إعادة المحاولة دون تكرار |
| الملفات | تخزين خاص متوافق مع S3 وروابط مؤقتة | صور المنتجات وإثباتات التسليم بصلاحيات مختلفة |
| التطوير والنشر | npm workspaces، Docker Compose محليًا، CI عبر GitHub Actions | إعداد قابل لإعادة التشغيل وفحوص لكل تغيير |
| الاختبارات | اختبارات وحدات، تكامل PostgreSQL، Playwright للمسارات الكاملة | اختبار القواعد والعزل والتزامن وتجربة الأطراف |

نبدأ بخادم واحد مقسم إلى وحدات؛ لا حاجة إلى Microservices أو Redis قبل ظهور حاجة مقاسة. بيانات الطلبات تظل في PostgreSQL. تختار M0 إصدارات مستقرة متوافقة من Node.js والحزم وتثبتها مع lockfile بعد تجربة البناء، دون افتراض أن أحدث إصدارات الأدوات متوافقة تلقائيًا.

```text
apps/
  web/                 # admin / supplier / merchant / driver
  api/                 # وحدات الأعمال وREST والعامل المؤجل
packages/
  contracts/           # عقود API العامة دون أسرار أو نماذج قاعدة خام
  ui/                  # مكونات RTL
  config/              # إعدادات مشتركة
prisma/                # schema + migrations + development seed
tests/e2e/
infra/                 # إعداد محلي ونشر ونسخ احتياطي
docs/
```

هذه شجرة مستهدفة في M0؛ الملفات البرمجية المذكورة لم تُنشأ ضمن تسليم التخطيط.

الوحدات: Identity، Organizations، Catalog، Pricing/Offers، Delivery Rules، Cart/Quotes، Orders/Inventory، Dispatch/Trips، Proof/Collections، Support/Ratings، Notifications، Reporting/Audit. لا تستدعي الواجهة قاعدة البيانات مباشرة ولا تقرر الصلاحيات أو السعر النهائي.

مراجع تقنية للتحقق وقت التأسيس: [Next.js installation](https://nextjs.org/docs/app/getting-started/installation)، [NestJS documentation](https://docs.nestjs.com/)، [Prisma transactions](https://www.prisma.io/docs/orm/fundamentals/transactions).

## 4. نموذج البيانات والقيود

| المجال | الجداول/الكيانات الرئيسية | قيود أساسية |
|---|---|---|
| الهوية | Users، Sessions، Roles، Memberships | عضوية المورد أو المحل وصلاحية الدور تتحقق خادميًا؛ حساب معطل لا يستمر بجلسة فعالة |
| الأطراف | Suppliers، SupplierStores، Merchants، MerchantAddresses | توثيق المورد منفصل عن تسجيله؛ العنوان يتبع محلًا محددًا |
| الكتالوج | Categories، ProductCatalog، SupplierProducts، CatalogRequests | هوية العبوة ثابتة؛ طلب منتج جديد يراجعه المدير؛ تعديل العبوة ينشئ تعريفًا جديدًا |
| التسعير | Offers، OfferTargets، MerchantGroups، OfferRedemptions | صلاحية زمنية، ملكية قائمة العملاء، أهلية، حدود استفادة ذرية |
| الخدمة | DeliveryZones، SupplierDeliveryRules، DeliverySlots | منطقة ويوم وفترة وcutoff وحد أدنى ورسوم وسعة؛ الحجز يمنع تجاوز السعة |
| الشراء | Carts، CartItems، Quotes، Orders، SubOrders، OrderItems | طلب فرعي لكل مورد في الطلب الرئيسي؛ لقطة مواصفات وسعر ورسوم وعنوان وموعد |
| المخزون | InventoryReservations، InventoryMovements | كمية متاحة غير سالبة، حجز محدود المدة وتحرير مرة واحدة |
| اللوجستيات | Drivers، DriverEmployers، DriverZones، Vehicles، Trips، TripStops، DeliveryTasks | جهة واحدة فعالة للسائق في MVP؛ مهمة نشطة واحدة للطلب الفرعي؛ الاستلام قبل التسليم |
| الإثبات | DeliveryEvents، DeliveryProofs، Collections | رمز مسلّم بصورة آمنة، مبلغ وعملة ومُحصّل وتأكيد استلام نقدي منفصل |
| الدعم | Complaints، ComplaintItems، Ratings | تخص طلبًا ومالكًا صحيحين؛ تقييم بعد التسليم وبقيد يمنع التكرار |
| التشغيل | Notifications، AuditLogs، OutboxEvents، IdempotencyKeys | مفتاح فريد لكل عملية قابلة للتكرار؛ سجل أحداث بتاريخ وهوية منفذ وارتباط بالطلب |

مبالغ المال تستخدم أعدادًا صحيحة بأصغر وحدة نقدية مقررة وcurrency صريحة؛ لا floating point. الكميات الوزنية تستخدم decimal مضبوطًا. وزن المنتج وحجمه بوحدات موحدة ومنفصلان عن محتوى العبوة، وقد تكون قيمتهما مجهولة.

تخزن الأوقات كـUTC، وتفسر جداول الخدمة حسب Asia/Damascus. تمنع القيود المرجعية ربط عرض أو مهمة أو شكوى بجهة غير صحيحة. لا يُحذف سجل طلب مكتمل عند إيقاف منتج أو مورد؛ تُحفظ اللقطات والتدقيق، مع سياسة لاحقة لإخفاء البيانات الشخصية.

## 5. معاملات الطلب والمخزون

1. `POST /v1/quotes`: يحسب الخادم الأهلية والكميات والحدود والرسوم والموعد والتوفر. النتيجة version وexpiresAt وتقسيم حسب المورد وتحذيرات السعر الذي ينتظر التأكيد.
2. `POST /v1/orders`: يستقبل quoteId ومفتاح Idempotency-Key. يعاد التحقق من العنوان ونسخة السعر والعرض والسعة والمخزون؛ إذا تغير شيء يُعاد عرض سعر جديد للموافقة، دون إنشاء طلب ناقص بصمت.
3. داخل معاملة واحدة: إنشاء الطلب الرئيسي والفرعيات واللقطات وحجوزات المخزون والمواعيد والاستفادة من العرض وأحداث Outbox. طلبان على آخر وحدة لا ينجحان معًا؛ فشل أحد البنود يلغي معاملة الإنشاء كاملة.
4. السعر المعروض ينتظر تأكيد المورد. المورد يقبل السعر والكميات المرسلة أو يرفض بسبب موثق. MVP لا يتيح تعديل السعر أو الاستبدال سرًا؛ عند الحاجة يرفض ويطلب المحل عرضًا جديدًا. هذا يبسّط التنفيذ مع احترام شرط تأكيد السعر.
5. الحجز المؤقت يُستهلك عند القبول، ويُحرر عند الرفض أو انتهاء مهلة القبول أو الإلغاء المسموح. مهلة القبول إعداد تشغيلي يحسم في M0. حجز الموعد يبقى حتى انتهاء الطلب أو إلغائه وفق السياسة.
6. سباق قبول المورد مع انتهاء الحجز يُحسم بالقفل/نسخة السجل؛ عملية واحدة فقط تنجح. حفظ طلب ثم انقطاع الاتصال يعيد الطلب نفسه عند المحاولة بالمفتاح ذاته؛ إعادة المفتاح مع جسم مختلف تُرفض.
7. بعد قبول مورد، رفض مورد آخر لا يلغي الأول تلقائيًا. يظهر للمحل أن الطلب الرئيسي جزئي، وأن رسوم كل شحنة تخص طلبها الفرعي. الإلغاء بعد القبول يحتاج مسار عمليات موثق، ويمنع بعد تسليم الحمولة دون إجراء معالجة واضح.
8. إرسال الإشعارات والملفات لا يحدث داخل معاملة حجز المخزون؛ يعالج Outbox بعد الحفظ، مع محاولات محدودة ومفتاح يمنع التكرار.

## 6. حالات التجارة والتوصيل

حالة الطلب الفرعي التجارية:

```text
PENDING_SUPPLIER → CONFIRMED → PREPARING → READY → FULFILLED
PENDING_SUPPLIER → REJECTED / EXPIRED / CANCELLED
CONFIRMED / PREPARING / READY → CANCELLED (ضمن سياسة وصلاحية محددة)
```

حالة مهمة التوصيل:

```text
UNASSIGNED → ASSIGNED → ACCEPTED → PICKED_UP → IN_TRANSIT → ARRIVED → DELIVERED
ASSIGNED → UNASSIGNED (رفض أو إعادة إسناد قبل الاستلام، مع سجل)
PICKED_UP / IN_TRANSIT / ARRIVED → FAILED
FAILED → ASSIGNED (إعادة محاولة مع معالجة مكان الحمولة وسجل المحاولة السابقة)
```

الإسناد مسموح عندما READY؛ نجاح DELIVERED يحتاج إثباتًا ويحوّل التجارة إلى FULFILLED ضمن معاملة. لا يقفز المورد إلى التسليم ولا يغير السائق سعر الطلب. إلغاء المهمة قبل الاستلام مرتبط بإلغاء الطلب؛ بعد الاستلام لا تحرر البضاعة افتراضيًا وكأنها في المستودع.

الشكاوى `OPEN → IN_REVIEW → RESOLVED / REJECTED` والتحصيل `UNPAID / PARTIAL / PAID / DISPUTED` مستقلان عن الحالتين. لا يؤدي فتح شكوى إلى محو تاريخ التسليم.

حالة الطلب الرئيسي مشتقة من الفرعيات: جميعها ملغاة/مرفوضة/منتهية تعني CLOSED_UNFULFILLED، جميعها مكتملة تعني COMPLETED، وجود فرع منفذ وآخر نهائي غير منفذ يعني PARTIALLY_FULFILLED، وبقاء أي فرع جارٍ يعني IN_PROGRESS مع عدادات مستقلة. تعرض تفاصيل الفرعيات دائمًا.

## 7. صلاحيات وإسناد وتوصيات

| الدور | نطاق الوصول والتغيير |
|---|---|
| Admin | اعتماد الأطراف والكتالوج والإعدادات والموظفين؛ الأعمال الحساسة مسجلة |
| Operations | متابعة الطلبات والشكاوى وإسناد سائقي رافد؛ دون إدارة صلاحيات المدير |
| Supplier | متجره وأسعاره وعروضه وطلباته وسائقوه؛ لا بيانات المورد الآخر |
| Merchant | عناوينه وسلته وطلباته والعروض المؤهل لها؛ المقارنة من API مخصص |
| Supplier Driver | مهامه المسندة ضمن المورد نفسه فقط |
| Platform Driver | مهامه المسندة من العمليات فقط، ولو شملت أكثر من مورد |

تعتمد الاستعلامات على هوية الجلسة وعضوية المنظمة؛ لا يؤخذ supplierId المرسل من العميل كإثبات صلاحية. تطبق القيود على API والبحث والإشعارات والتصدير وروابط الإثبات والذاكرة المؤقتة أيضًا. لا يجوز cache مشترك للعروض الخاصة دون تضمين هوية المحل والأهلية.

التوصيل: يتحقق الخادم من جهة السائق وتوفره ودوامه والمنطقة والموعد والمركبة وحد الطلبات والمحطات. لا تضم رحلة سائق المورد طلب مورد آخر. تسمح رحلة رافد بموردين مختلفين عندما تكون الخدمة مفعلة مع استلام مستقل لكل مورد.

تحسب الحمولة على كل جزء بين محطتين، فلا تتجاوز السعة في أي نقطة. يمنع ترتيب تسليم قبل استلام بضاعته أو إسناد طلب إلى رحلتين نشطتين. قفل الرحلة والمركبة يمنع تجاوز السعة عند الإسناد المتزامن. عند نقص بيانات الوزن/الحجم يظهر «تقدير حمولة» وتطلب مراجعة عمليات وحدًا محافظًا لعدد الطلبات؛ لا تعرض علامة تحقق وزن دقيقة.

التوصية الأولى خوارزمية قواعد معلنة: تصفية العروض غير المؤهلة والمنتهية وغير المتاحة، ثم اقتراح خطط صالحة تشمل رسوم المورد والحد الأدنى والمواعيد. مقارنة سعر كل بند وحده قد تنتج سلة أغلى بعد التوصيل؛ لذلك تقارن إجماليات الخطط كاملة. يمكن تجربة التوزيعات كاملة في سلة صغيرة بحد معلن، واستخدام heuristic بسقف حسابي بعدها. توصف النتيجة «أفضل خطة ضمن الخيارات المفحوصة» ولا تدعي الحل الأمثل عالميًا.

التوفير = `(referenceTotal - recommendedTotal) / referenceTotal × 100` فقط لمرجع موجب وصالح وبنفس المنتجات والكميات والخدمة. لا تدخل مقارنة عبوات مختلفة أو مرجع ناقص الرسوم. إذا كانت البيانات غير كافية تعرض رسالة غياب المقارنة، وإذا كان الفرق سالبًا تعرض فرق التكلفة دون ادعاء توفير. ترتيب السعر مستقل عن أي إعلان مدفوع؛ بقية أوزان الترتيب إعدادات معلنة وليست أرقامًا تجارية مفترضة.

## 8. مراحل التنفيذ ومعايير القبول

التقدير **10–15 أسبوع عمل تقويمي** بافتراض مطورين متفرغين مع مشاركة تصميم واختبار وتشغيل. كل أسبوع خمسة أيام؛ المدد تشمل تحقق المرحلة، ولا تشمل انتظار بيانات الموردين أو مزودي الخدمات أو تغيير النطاق. يحتاج المطور المنفرد إعادة تقدير بعد M0، وهذا ليس موعد إطلاق ملزمًا.

| المرحلة | المدة المقترحة | العمل | بوابة القبول والتبعية |
|---|---|---|---|
| M0: التأسيس | أسبوع | ADR تقني، workspace، API/web، قاعدة محلية، CI، RTL، عقود وأخطاء، مصفوفة صلاحيات وسياسات | تشغيل من clone نظيف، migration وseed، health، build/lint/typecheck، اختبار اتصال DB؛ أساس بقية المراحل |
| M1: الهوية والأطراف والكتالوج | 1–2 أسبوع | دخول وجلسات، التسجيل، اعتماد المورد، إدارة المحلات والعناوين والمناطق والمنتج وطلب إضافة منتج | موردان لا يقرآن بيانات بعضهما؛ حساب موقوف ممنوع؛ اختلاف العبوة يمنع المطابقة؛ بعد M0 |
| M2: أسعار وخدمة وشراء | 1–2 أسبوع | تحديث المخزون والأسعار، استعراض وبحث ومقارنة، قواعد خدمة ومواعيد، سلة وquote | سلة بموردين تعرض الرسوم والمواعيد والحدود؛ منطقة غير مخدومة لا تؤكد؛ بعد M1 |
| M3: الطلب والتجهيز | أسبوعان | معاملات وحجز وتزامن، قبول/رفض، تجهيز، تتبع مستقل، تدقيق وإشعارات الحالة | موردان ينتجان طلبًا رئيسيًا وفرعيين؛ آخر وحدة لا تباع مرتين؛ إعادة الطلب لا تكرر الإنشاء؛ بعد M2 |
| M4: التوصيل والتحصيل | أسبوعان | سائقا المورد والمنصة، مركبات، إسناد ورحلات ومحطات، إثبات ورمز، فشل وإعادة محاولة وتحصيل | مسارا التوصيل ورحلة بطلبين يعملان؛ رفض سائق/منطقة/سعة خاطئة؛ فشل تسليم لا يفشل الآخر؛ بعد M3 |
| M5: اكتمال وظائف MVP | 2–3 أسابيع | عروض عامة وخاصة ومجموعات وحدود، توصيات وتوفير، بلاغات وتقييمات، تقارير المورد والإدارة | عرض خاص غير مكشوف؛ حدود الاستفادة لا تتجاوز بالتزامن؛ مرجع توفير صحيح؛ شكوى وتقييم وتقرير من بيانات حقيقية؛ بعد M3، وتحقق دورة التوصيل بعد M4 |
| M6: التحقق والإطلاق التجريبي | 1–2 أسبوع | اختبارات شاملة، أمان وأداء، staging، نسخ واستعادة، تدريب ومراقبة وتشغيل | نجاح السيناريوهات في القسم 10 واعتماد سياسات التشغيل ثم تجربة محدودة؛ بعد M4 وM5 |

تُربط كل مرحلة بـPR واختبارات وملاحظات تشغيل؛ لا يُعتبر نموذج بيانات تجريبي أو واجهة mock دليل اكتمال وظيفة تجارية.

## 9. عقود API والشاشات المستهدفة

العقود التالية مقترحة وليست endpoints منفذة. توثق M0 pagination وvalidation وrequestId وأكواد أخطاء ثابتة؛ يستخدم 403 للصلاحيات و409 لتعارض السعر/الحالة و422 لقواعد العمل غير المستوفاة.

| المجال | نماذج العقود | الشاشات |
|---|---|---|
| الهوية والأطراف | `/v1/auth/*`, `/v1/me`, `/v1/suppliers`, `/v1/merchant-addresses` | دخول، تسجيل محل، اعتماد المورد، حساب المتجر والعناوين |
| المنتجات والخدمة | `/v1/catalog`, `/v1/catalog-requests`, `/v1/supplier-products`, `/v1/delivery-rules` | دليل الإدارة، منتجات المورد، جدول الخدمة، بحث المحل والمقارنة |
| الشراء | `/v1/cart`, `/v1/quotes`, `/v1/orders`, `/v1/suborders/:id/actions` | السلة حسب المورد، التأكيد، طلبات المورد، تتبع المحل |
| التشغيل | `/v1/drivers`, `/v1/trips`, `/v1/delivery-tasks`, `/v1/delivery-proofs`, `/v1/collections` | قائمة الإسناد، الرحلة ومحطاتها، مهام السائق، التسليم والتحصيل |
| اكتمال MVP | `/v1/offers`, `/v1/purchase-plans`, `/v1/complaints`, `/v1/ratings`, `/v1/reports`, `/v1/notifications` | العروض، التوصيات، البلاغات، التقييم، التقارير والإشعارات |

تكون تغييرات الحالة actions محددة الصلاحية والتحقق، لا حقل status قابلًا للتعديل الحر. تحديث شاشة الحالة يمكن أن يبدأ باستعلام دوري أثناء فتحها؛ الإشعارات الخارجية تحتاج adapter ومزودًا معتمدًا لاحقًا.

## 10. التحقق وتعريف الإنجاز

| الاختبار | النتيجة المطلوبة | المرحلة |
|---|---|---|
| مقارنة منتج واحد لدى موردين، ثم تغيير حجم أو عدد قطع العبوة | مقارنة الأول ورفض مساواة الثاني | M1–M2 |
| مستخدم مورد يغير IDs في API، وسائق يفتح مهمة غير مسندة | لا كشف ولا تعديل، بما فيه الإثباتات والإشعارات | M1–M6 |
| عرض خاص بمحل A يُطلب من B أو تنتهي صلاحيته | لا ظهور ولا تطبيق، حتى عبر quote محفوظ | M5 |
| سلة موردين مع رسوم وحد أدنى وcutoff وموعد ممتلئ | إجمالي مطابق للرسوم المعلنة ومنع الحجز غير الصالح | M2–M3 |
| تأكيدان متزامنان على آخر مخزون وآخر سعة موعد/عرض | لا تجاوز لأي حد؛ فشل ذري واضح | M3/M5 |
| انقطاع اتصال بعد حفظ طلب ثم إعادة التأكيد | نفس الطلب دون تكرار بنود أو حجوزات | M3 |
| قبول مورد ورفض آخر أو انتهاء مهلة حجزه | الأول يستمر والثاني نهائي غير منفذ مع تحرير موارده مرة واحدة | M3 |
| سائق تابع لمورد آخر أو خارج الدوام/المنطقة | الإسناد مرفوض | M4 |
| رحلة تستوعب طلبين ثم إضافة ثالث يتجاوز السعة أو تسليم قبل الاستلام | رفض التعديل والحفاظ على الرحلة الصحيحة | M4 |
| فشل طلب واحد في الرحلة وإكمال الآخر | حالات وإثباتات وتحصيلات مستقلة | M4 |
| رمز تسليم خاطئ أو منتهي أو مُعاد استخدامه، وإعادة إرسال مبلغ التحصيل | رفض الرمز ومنع تكرار تسجيل النقد؛ لا تسليم بلا إثبات | M4 |
| تغيير سعر بعد quote أو أثناء قبول المورد | إعادة موافقة أو رفض؛ لا زيادة خفية أو تغيير لقطة الطلب | M3 |
| مرجع توفير صفر أو ناقص الرسوم أو أعلى من تكلفة الخطة بصورة غير مكافئة | لا نسبة مضللة؛ عرض سبب عدم المقارنة | M5 |
| شكوى نقص بعد التسليم وتقييم قبل التسليم | قبول الشكوى مع حفظ التسليم ورفض التقييم المبكر | M5 |
| دورة كاملة للأدوار على جوال وRTL ولوحة مفاتيح واتصال متقطع | إعادة المحاولة آمنة، رسائل واضحة، لا تأكيد مكرر | M6 |
| استعادة نسخة DB وملفات الإثبات على بيئة منفصلة | إعادة فتح الطلبات ومطابقة المجاميع وسجل الأحداث | M6 |

كل ميزة مكتملة تحتاج تحقق صلاحية وملكية، validation، مهاجرة عند الحاجة، معالجة خطأ، عقود محدثة واختبار خطر العمل الفعلي. يفحص CI البناء والأنواع والتنسيق/الـlint والوحدات والتكامل؛ E2E يغطي الدورة الكاملة قبل الإطلاق. لا يكفي نجاح build لإعلان MVP جاهزًا.

تُنشأ بيانات اختبار ثابتة: موردان وثالث موقوف، محلان، منطقتان، منتجات متطابقة وأخرى مختلفة العبوات، عروض عامة وخاصة ومنتهية، سائقا مورد وسائق رافد، مركبة محدودة، وطلب تعذر تسليمه. لا تستخدم بيانات عملاء حقيقية في seed.

## 11. قرارات العمل المفتوحة

تبدأ M0 بالافتراضات التالية محليًا، وتُراجع قبل تفعيل أي تشغيل تجاري. لا يتطلب البدء التقني اختراع نسب عمولة أو أسعار توصيل أو بيانات موردين.

## 12. النشر والمراقبة والتجربة

1. بيئات local وstaging وproduction منفصلة؛ أسرار خارج Git، cookies آمنة وCSRF عند استخدام جلسات cookies، rate limits وحماية الدخول والرموز. لا تسجل كلمات المرور أو OTP أو العناوين الكاملة في logs.
2. CI يبني ويفحص مهاجرات واختبارات التكامل على قاعدة مؤقتة. ينشر staging من commit معروف، وproduction من إصدار مختبر بإعدادات فعلية مع فحص صحة.
3. المهاجرات تستخدم توسعة ثم انتقالًا قبل الحذف؛ فشل نشر التطبيق يعاد إلى الصورة السابقة إذا كانت متوافقة. تغيير البيانات المدمر يحتاج نسخة واستراتيجية استعادة محددة، ولا يفترض أن downgrade آمن.
4. اختبارات حمل قبل M6: سيناريو مبدئي 50 جلسة و10 تأكيدات متزامنة، بهدف مقترح p95 أقل من ثانيتين للقراءة وثلاث للتأكيد دون مزود خارجي؛ هذه أهداف للتحقق وليست قياسات منجزة.
5. تنبيهات للأخطاء وتأخر القبول وحجوزات منتهية وعامل Outbox متعثر ومهام غير مسندة. ربط requestId بالأحداث دون تسريب البيانات الشخصية.
6. نسخ DB يومي مبدئيًا وتخزين إثباتات محمي؛ هدف تجريبي RPO لا يزيد عن 24 ساعة وRTO أربع ساعات يخضع لموافقة التشغيل. تُجرّب الاستعادة قبل استقبال طلبات حقيقية.
7. تبدأ التجربة المقترحة بـ5–10 موردين و20–30 محلًا ومنطقة أو منطقتين وفق الوثيقة. يدرّب المورد والسائق والعمليات على التعذر والنقد والشكاوى، وتوفر قناة دعم واضحة.
8. تتابع لوحة المؤشرات: الطلبات الرئيسية والفرعية دون مضاعفة GMV، القبول والإكمال والتأخر، موردون ومحلات نشطة، تحديث الأسعار، إعادة الطلب، التحصيل والشكاوى والتوفير المؤكد. لا تعرض «توفير فعلي» قبل تحقق التكلفة النهائية.

بوابة التوسع: نجاح السيناريو الكامل في القسم 17 من المصدر، بيانات أسعار موثوقة، طلبات مكتملة ومتكررة، قدرة على إدارة الاستثناءات، وقياس تكلفة الخدمة. لا يُعلن التوسع بمجرد انقضاء الأسابيع.
